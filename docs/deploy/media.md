# Voice and the lounge TV: the `media` profile (LiveKit)

Proximity voice chat and screen sharing to the lobby's lounge TV (SPEC §9.4, D5)
run on a self-hosted [LiveKit](https://livekit.io) server under the Compose
profile `media`. They are optional: without it the office works as before, the
voice and share buttons are hidden, the TV shows "Screen share is off on this
office" and Settings says how to turn them on.

## How it fits together

```
browser ──HTTPS/WSS 443──▶ Caddy ──/livekit/*──▶ livekit:7880   signalling (WebSocket)
browser ──HTTPS 443──────▶ Caddy ──────────────▶ office:4600    POST /api/media/token
browser ◀──UDP 7882 / TCP 7881──▶ livekit (host ports)          audio and video
```

- **The office never carries media.** It mints a short-lived LiveKit token
  (10 minutes; LiveKit refreshes it for connected clients) for a signed-in
  human, for one of their own building sessions, with the grants their role
  allows: owners, admins and members may talk and share; viewers listen and
  watch. Browsers then talk to LiveKit directly.
- **Signalling goes through Caddy on 443** at `https://<your domain>/livekit`,
  so there is no extra hostname, certificate or port for it.
- **Media uses one UDP port (7882)** for every participant (LiveKit's UDP
  mux), with **TCP 7881** as the fallback for networks that block UDP. Both
  are published by the `livekit` service on the host.
- One LiveKit room per office. Loudness by distance is computed in each
  browser; who may hear a voice at all is enforced by LiveKit: a voice in a
  project room is only sent to the people in that room.

## Turn it on

On the VM, from the checkout:

```sh
scripts/setup.sh --media
```

This generates `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` into `deploy/.env`
(mode 600, never printed, never committed), sets `COMPOSE_PROFILES=media` so
every later `docker compose up` and `scripts/setup.sh` run starts LiveKit too,
starts it and checks that `https://<domain>/livekit/` answers. Then open the
firewall (next section).

By hand instead: put a key (letters and digits, e.g. `API` + 16 hex
characters) and a secret of at least 32 characters into `deploy/.env`, then

```sh
cd deploy
docker compose --profile media up -d
```

`livekit.yaml` is generated by Compose from `deploy/.env` on every `up`
(`configs.livekit-yaml` in `docker-compose.yml`); it holds no secret: LiveKit
reads the key pair from the `LIVEKIT_KEYS` environment variable.

To turn media off again: remove `COMPOSE_PROFILES=media` and empty both keys in
`deploy/.env`, then `docker compose up -d --remove-orphans` (or
`docker compose stop livekit`).

## Firewall

Open, inbound, on the VM and in the cloud provider's firewall:

| Port | Protocol | What |
|---|---|---|
| 443 | TCP | Already open for the office: HTTPS and LiveKit signalling (`/livekit`) |
| 7881 | TCP | LiveKit media over TCP (fallback when UDP is blocked) |
| 7882 | UDP | LiveKit media (all participants, one port) |
| 3478 | UDP | Only with the optional TURN relay (below) |
| 5349 | TCP | Only with the optional TURN over TLS (below) |

Changed `LIVEKIT_TCP_PORT` / `LIVEKIT_UDP_PORT` in `deploy/.env`? Open those instead.

### ufw

```sh
sudo ufw allow 7881/tcp comment 'LiveKit media (TCP)'
sudo ufw allow 7882/udp comment 'LiveKit media (UDP)'
sudo ufw status
```

Note: ports Docker publishes are reachable even without these rules, because
Docker inserts its own iptables rules ahead of ufw's. Add them anyway (they
document the intent and are needed if LiveKit ever runs outside Docker), and
rely on the cloud firewall to actually filter. To restrict Docker-published
ports on the host itself, use the `DOCKER-USER` chain.

### iptables (without ufw)

```sh
sudo iptables -A INPUT -p tcp --dport 7881 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 7882 -j ACCEPT
# persist, e.g. Debian/Ubuntu: sudo apt install iptables-persistent && sudo netfilter-persistent save
```

### Cloud firewall (any provider)

Add inbound rules to the VM's firewall / security group:

- TCP 7881 from `0.0.0.0/0` and `::/0`
- UDP 7882 from `0.0.0.0/0` and `::/0`

Hetzner Cloud: *Firewalls → Rules → Inbound*; DigitalOcean: *Networking →
Firewalls → Inbound Rules*; AWS: the instance's security group, *Inbound
rules* (Custom TCP 7881, Custom UDP 7882). Outbound needs nothing special.

## The public IP LiveKit advertises

Browsers send media to the address LiveKit tells them. On a VPS with a public
IP the default (`LIVEKIT_USE_EXTERNAL_IP=true`) finds it with STUN at start-up;
check it in the logs:

```sh
cd deploy && docker compose logs livekit | grep "starting LiveKit server"
# ... "nodeIP": "203.0.113.10", "rtc.portTCP": 7881, "rtc.portUDP": {"Start":7882,...}
```

If STUN is blocked or the IP is wrong, set it: `LIVEKIT_NODE_IP=203.0.113.10`.
For an office only on a LAN or a Tailscale network: `LIVEKIT_USE_EXTERNAL_IP=false`
and `LIVEKIT_NODE_IP=<the LAN or tailnet IP>`. `scripts/setup.sh --media` on a
`localhost` domain sets `127.0.0.1` for you.

## Verify

1. `curl -fsS https://<domain>/livekit/` prints `OK` (LiveKit through Caddy).
2. `docker compose logs livekit` shows the public `nodeIP` and the ports above.
3. From another machine: `nc -vz <domain> 7881` connects. (UDP cannot be
   checked this way; the browser test below covers it.)
4. Two people (or two browsers) sign in. The corner of the HUD shows **Voice**
   with a green lamp. One clicks **Mic on** and talks: the other hears them,
   louder when standing close, silent from about 18 m, and sees their genius's
   mouth move. **Mute mic** shows "Muted" over their head.
5. In the lobby, **Share screen** (or `E` at the lounge TV) and pick a
   window: the picture plays on the TV for everyone in the lobby; sitting on the
   sofa opens it full screen. **Stop sharing** ends it; an owner or admin can
   take someone else's screen off the TV from the full-screen view.

If the lamp turns red with "Could not reach the voice server", signalling
fails: check `/livekit/` (step 1) and `LIVEKIT_URL`. If it connects but nobody
hears anyone, media does not get through: check the firewall rules and the
advertised IP; a network that blocks UDP still works over TCP 7881, slower; for
networks that block both, use TURN.

For developers there is a scripted version of steps 4 and 5 with two headless
Chromiums and fake devices: `tests/e2e/media/media.verify.ts` (its header has
the command).

## TURN (optional)

Most people never need it. It helps people behind networks that block UDP and
non-standard TCP ports (some corporate and hotel networks), by relaying media
over UDP 3478 or, more often allowed, TLS.

### LiveKit's built-in TURN over UDP

In `deploy/.env`:

```sh
LIVEKIT_TURN_ENABLED=true
# LIVEKIT_TURN_DOMAIN=office.example.com   (default: OFFICE_DOMAIN)
```

and publish the port with a `deploy/docker-compose.override.yml` (Compose
reads it automatically):

```yaml
services:
  livekit:
    ports:
      - "3478:3478/udp"
```

Open UDP 3478 in the firewalls, then `docker compose up -d`.

### LiveKit's built-in TURN over TLS

TURN/TLS needs a certificate for the TURN domain. Caddy already has one for
`OFFICE_DOMAIN`; mount Caddy's data read-only and point LiveKit at it. Port 443
is taken by Caddy, so use 5349 (or a second IP address for 443):

```yaml
# deploy/docker-compose.override.yml
services:
  livekit:
    ports:
      - "3478:3478/udp"
      - "5349:5349/tcp"
    volumes:
      - caddy-data:/caddy:ro
```

```sh
# deploy/.env (replace office.example.com with your OFFICE_DOMAIN)
LIVEKIT_TURN_ENABLED=true
LIVEKIT_TURN_TLS_PORT=5349
LIVEKIT_TURN_CERT_FILE=/caddy/caddy/certificates/acme-v02.api.letsencrypt.org-directory/office.example.com/office.example.com.crt
LIVEKIT_TURN_KEY_FILE=/caddy/caddy/certificates/acme-v02.api.letsencrypt.org-directory/office.example.com/office.example.com.key
```

LiveKit reads the certificate at start, so restart it after Caddy renews
(`docker compose restart livekit`, e.g. monthly from cron). LiveKit refuses a
certificate that does not match the TURN domain.

### An external coturn

To use a TURN server you already run, give LiveKit your own config file:

```yaml
# deploy/docker-compose.override.yml
services:
  livekit:
    configs: !override
      - source: livekit-custom
        target: /etc/livekit.yaml
configs:
  livekit-custom:
    file: ./livekit.custom.yaml
```

Start `deploy/livekit.custom.yaml` from the generated one
(`docker compose --profile media config` prints it under `configs:`) and add:

```yaml
rtc:
  turn_servers:
    - host: turn.example.com
      port: 3478
      protocol: udp
      username: office
      credential: <the coturn user's password>
```

Keep secrets out of it where you can (the key pair still comes from
`LIVEKIT_KEYS`), and keep the file out of git.

## Larger offices

One UDP port is plenty for a team. For hundreds of simultaneous participants
LiveKit recommends a UDP port range with host networking. Switch with an
override that sets `network_mode: host` on `livekit`, a custom config (above)
with `rtc.port_range_start: 50000` / `port_range_end: 60000` instead of
`udp_port`, and `LIVEKIT_URL=wss://livekit.example.com` behind its own Caddy
site block (`reverse_proxy 127.0.0.1:7880` from a host-networked Caddy, or
`host.docker.internal:7880`); then open UDP 50000-60000 instead of 7882.
